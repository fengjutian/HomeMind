## 一、开始前先确认上下文

实现或修改前，从仓库和用户信息中确认：

- 应用、模块及功能目标；
- Kotlin/Java、Compose/View、架构和依赖注入方式；
- Gradle、Android Gradle Plugin、Kotlin、JDK 与依赖版本；
- `minSdk`、`targetSdk`、`compileSdk` 和支持的设备形态；
- 数据来源、缓存、离线、登录和权限要求；
- 导航、主题、多语言、无障碍和设计系统；
- 已有测试、CI、发布渠道、签名和构建变体。

信息不足但不影响方向时，明确假设并继续；如果选择会改变公开 API、数据模型、最低版本或整体架构，先提出一个简短问题。

## 二、工作原则

### 2.1 先定位，再修改

- 先阅读相关模块、调用链、状态来源和测试，找出最小修改面。
- 诊断崩溃时沿异常链寻找首个有意义的业务栈帧，不把最后出现的错误当成根因。
- 诊断性能时先建立可复现条件、基线与指标，不凭体感优化。
- 构建失败先记录完整任务、变体、版本和首个失败原因，不在错误尾部猜测。

### 2.2 尊重生命周期和状态

- UI 状态使用不可变模型，区分加载、空、成功、失败和部分数据。
- Compose 中保持单向数据流，避免在重组期间执行副作用；正确使用 `remember`、`rememberSaveable` 和 Effect API。
- View/XML 项目尊重 Fragment View 生命周期，避免持有失效 View、Context 或 Activity。
- 协程必须有明确作用域、调度器与取消路径；不得用 `GlobalScope` 规避生命周期。
- Flow 的冷热、共享、重放与收集生命周期必须符合数据语义，不重复启动昂贵上游。
- 进程死亡和配置变更是正常场景；需要恢复的轻量状态进入 `SavedStateHandle`，持久业务数据进入存储层。

### 2.3 分层与数据边界

- 根据项目规模选择足够简单的架构，不为小功能制造多层空转抽象。
- UI 不直接承担网络、数据库或复杂业务规则；Repository 也不变成无边界的万能类。
- 明确数据所有权、缓存真相来源、刷新策略、错误映射和并发写入规则。
- Room schema 变更提供迁移和测试；不能用破坏性迁移掩盖生产数据问题。
- 网络请求处理超时、取消、重试、幂等、分页和鉴权失效；不无限重试。

## 三、界面实现

### Jetpack Compose

- Composable 尽量无状态；状态提升到最小合理所有者。
- 稳定 key、列表状态、派生状态和数据类型，避免无意义重组。
- 覆盖加载、空、错误、离线、成功和权限拒绝状态。
- 支持系统返回、深链、窗口尺寸变化、键盘、边到边显示和状态恢复。
- 提供语义、内容描述、触控尺寸、对比度和动态字体支持。
- 对关键组件提供 Preview，对关键流程提供 Compose UI 测试。

### View/XML

- 使用 ViewBinding 或项目既有安全绑定方式，避免生命周期外访问 View。
- RecyclerView 正确使用 DiffUtil、稳定标识、复用和分页。
- 不为追求“现代化”强制把稳定页面迁移到 Compose；新旧体系可以通过清晰边界渐进共存。

## 四、并发与后台任务

- 短生命周期 UI 工作使用与界面绑定的协程作用域。
- 必须在应用离开后继续、允许延迟执行的可靠任务使用 WorkManager，并声明约束、唯一性和退避策略。
- 前台服务只用于平台允许且用户可感知的长期任务，正确处理通知与新版本限制。
- 广播、Service、ContentProvider 和回调全部有清晰注册、注销与异常路径。
- 不在主线程执行网络、数据库、大文件、图像解码或重计算。

## 五、性能、电量和稳定性

- 使用可复现基准、Profiler、Perfetto、Macrobenchmark、StrictMode、系统统计或线上指标证明问题与改进。
- 启动优化区分冷、温、热启动，审查 Application 初始化、ContentProvider、首帧与懒加载。
- 卡顿分析关注主线程阻塞、过度绘制、重组、布局、图片和 GC，不盲目增加缓存。
- 内存问题检查生命周期泄漏、Bitmap、大集合、缓存上限和后台组件。
- 电量问题检查唤醒、定位、传感器、网络批处理、后台限制和任务频率。
- ANR 必须结合主线程栈、锁竞争、Binder、I/O 和发生场景分析。

## 六、安全、隐私与兼容性

- 密钥和长期凭证不写入客户端源码、资源或版本库。
- 敏感数据按威胁模型选择 Keystore、加密存储与传输保护；日志不输出令牌和个人数据。
- 权限按需申请，并处理拒绝、永久拒绝和系统设置返回路径。
- 导出组件、Intent、Deep Link、WebView、文件共享和反序列化均验证不可信输入。
- 使用版本检查、AndroidX 兼容 API 和设备能力检测处理系统差异，不依赖品牌或机型字符串硬编码。
- 涉及 Play 政策、Target API 或平台行为时，查证当前官方文档，不凭过时记忆下结论。

## 七、构建与发布

- 版本组合以项目 wrapper、version catalog、插件声明和官方兼容表为准。
- 修复依赖冲突时解释解析结果，不随意强制整个依赖树使用某版本。
- 明确 debug/release、product flavor、签名配置、资源覆盖和环境变量边界。
- R8/ProGuard 问题用 mapping、missing rules 和反射入口定位；保留规则尽可能精确。
- 发布前验证 AAB/APK、签名、版本号、权限、隐私声明、原生库架构、资源和升级安装。
- 不在回复中泄露签名文件、密码、服务账号或其他凭证。

## 八、测试策略

- 业务规则、状态转换和数据映射优先使用快速单元测试。
- Repository 测试覆盖缓存、网络、数据库、失败与竞争条件。
- UI 测试聚焦关键用户流程、状态渲染、导航和无障碍语义，不依赖脆弱延时。
- 数据库迁移、深链、进程恢复、配置变更和关键兼容性路径需要专项测试。
- 修复缺陷时先增加能够复现问题的回归测试，再验证修复。

## 九、代码修改与交付

- 修改现有仓库时遵守其贡献指南、模块边界、命名、格式和测试命令。
- 只改动任务相关文件，不顺手迁移框架、升级依赖或统一无关风格。
- 提供可以直接编译的必要代码和 import；省略上下文时清楚标记插入位置。
- 不声称未执行的构建、测试、设备验证或性能测量已经通过。
- 最终说明：实现结果、关键取舍、修改文件、验证命令、设备或版本覆盖，以及仍需确认的风险。
