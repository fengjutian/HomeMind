# HomeMind 家庭 AI OS 演进目标

## 1. 愿景

HomeMind 的长期目标是成为运行在 Windows、Linux、macOS、NAS 和家庭边缘设备之上的**家庭 AI 操作层**：统一管理家庭成员、智能体、设备、数据、任务、自动化与外部服务，让用户通过自然语言或确定性规则安全地感知、决策和执行。

HomeMind 不以替代传统操作系统内核、驱动或系统服务为目标。“OS”在本文中指面向家庭场景的资源、能力、权限、事件和应用控制平面。

## 2. 核心原则

- **本地优先**：家庭数据和关键自动化应尽可能在本地运行，云端能力按需使用。
- **确定性执行**：LLM 负责理解、规划和建议；确定性引擎负责授权、执行、重试和恢复。
- **最小权限**：用户、Agent、Skill、Plugin 和设备仅获得完成任务所需的权限。
- **可解释、可追溯**：敏感操作必须能回答谁发起、为何执行、访问了什么以及结果如何。
- **离线可用**：断网或云服务不可用时，家庭关键能力仍可工作。
- **渐进演进**：复用现有家庭、设备、权限、事件、任务、事务和智能家居模块，不建设传统 OS 内核。

## 3. 家庭中枢部署架构

HomeMind 在家庭中承担 AI、身份、数据、权限、审批和自动化控制平面的角色，不直接承担 Zigbee、Thread、蓝牙等无线协议控制器，也不替代 Home Assistant。

```text
手机 / 电脑 / 消息平台
          │
       HomeMind
   AI、家庭数据、权限、审批
          │
 Home Assistant / MQTT
          │
Matter / Zigbee / Wi-Fi / 蓝牙设备
```

架构边界：

- Home Assistant 负责厂商集成、设备发现、无线协议和物理设备到实体的映射。
- HomeMind 同步标准化设备状态与能力，应用家庭权限和事务审批，并只向 Agent 与自动化开放经过审查的命令目录。
- 厂商账号与凭据保留在 Home Assistant 或加密凭据库中，不复制到 Agent 提示词、普通配置或工作区。
- 门锁、摄像头、安防面板、燃气阀等高风险设备，在写入路径完成独立安全评审前保持只读。
- 部署在 NAS 或家庭电脑上的 Device Runtime 是受控的边缘文件执行节点，不是智能家居协议网关。

### 3.1 推荐硬件档位

以下配置是容量规划建议，不是软件安装的硬性最低要求。实际需求主要由本地模型、知识索引、家庭文件规模和并发量决定。

| 场景 | 主机建议 | 内存 | 系统与应用存储 | 模型方式 |
| --- | --- | ---: | ---: | --- |
| 个人体验 | 现有 Windows、macOS 或 Linux 电脑 | 4 GB 起 | 10–20 GB 可用空间 | 云端模型优先 |
| 家庭长期运行 | 常开 x86 小主机或 NAS | 8 GB 推荐 | 128 GB SSD 起 | 云端模型 |
| 同机运行 Home Assistant | N100/N150 级或更高主机 | 8–16 GB | 256 GB SSD 起 | 云端模型 |
| 本地运行 7B/8B 量化模型 | 近年 Intel/AMD 主机 | 16–32 GB | 512 GB SSD 起 | Ollama |
| 本地运行更大模型 | 独立 GPU 主机 | 32–64 GB | 1 TB SSD 起 | 按显存选择模型 |

多数家庭可从“低功耗 x86 小主机、16 GB 内存、512 GB NVMe、有线千兆网络、云端模型”起步。本地大模型不是家庭中枢成立的前提，也不应让 AI 推理与关键设备自动化形成单点资源争用。

### 3.2 协议与配套硬件

- 纯 Wi-Fi 或 Matter-over-Wi-Fi 设备通常不要求 HomeMind 主机增加无线协调器。
- Zigbee 设备需要 Home Assistant 支持的 Zigbee 协调器。
- Matter-over-Thread 设备需要 Thread Border Router。
- 蓝牙设备需要主机蓝牙或独立蓝牙代理。
- MQTT 设备需要启用认证、TLS 与 topic 白名单的 Broker；Broker 可与中枢同机部署。
- USB 无线协调器宜通过延长线远离主机、机箱和 USB 3.0 接口，以降低 2.4 GHz 干扰。

### 3.3 长期运行基线

- 服务器优先使用有线网络，并配置固定地址或 DHCP 保留地址。
- `OCTOP_HOME` 必须位于持久化存储；系统升级前创建备份，并将副本保存到另一设备或介质。
- RAID 提供可用性但不能替代备份；家庭照片与文件的数据盘应独立按容量规划。
- 推荐使用 UPS，降低突然断电对数据库和存储的影响。
- 远程访问应使用 VPN 或配置正确的 HTTPS 反向代理，不直接暴露未加密的 `8088` 端口。
- 关键规则应能在无 LLM、无公网的情况下执行；云端模型和外部连接器故障不能阻断基础家庭自动化。

## 4. P0：形成家庭 AI OS 的核心闭环

### 4.1 统一资源模型

目标：为家庭、成员、设备、资产、记忆、知识、任务、日历和自动化建立一致的资源表达。

需要补齐：

- 全局稳定的资源 ID、资源类型和版本化元数据。
- 所有者、家庭归属、可见范围和生命周期状态。
- 可查询的资源关系，例如“成员拥有设备”“资产属于相册”“任务涉及成员”。
- 统一的资源定位方式，例如 `homemind://devices/{id}`。
- 统一搜索、订阅、审计和权限检查入口。

验收标准：

- 任一核心资源都能通过统一 ID 定位并获得类型、归属和权限信息。
- 跨领域关系无需调用方了解各模块的数据库结构。
- 新资源类型可以接入统一搜索、审计和授权流程。

### 4.2 统一能力模型

目标：用与厂商无关的能力描述设备、平台和外部服务可以执行的动作。

需要补齐：

- 标准能力命名，如 `switch.on`、`climate.set_temperature`、`calendar.create_event`。
- 输入、输出和错误的版本化 Schema。
- 风险等级、确认策略和所需权限。
- 幂等键、超时、取消、重试和补偿语义。
- 执行结果与真实状态回读，区分“已受理”和“已生效”。

验收标准：

- 同一种能力可由不同厂商设备或 Connector 实现。
- Agent 和自动化引擎只依赖标准能力，不直接依赖厂商 API。
- 高风险能力无法绕过授权和确认流程。

### 4.3 细粒度权限与身份代理

目标：明确谁可以以谁的身份，对什么资源执行什么动作。

需要补齐：

- 用户—角色—资源—动作四维授权。
- Agent、Skill、Plugin 和 Connector 的权限声明。
- 一次性、限时、会话级和长期授权。
- 管理员、成人、儿童、老人和访客等家庭角色策略。
- 授权撤销即时生效，敏感访问全部进入审计记录。
- 明确显示执行主体、授权主体和最终责任人。

验收标准：

- 每次敏感调用都能解释授权来源。
- 私有资源不能因同属一个家庭而被默认共享。
- 权限撤销后，后台任务和离线设备也无法继续使用旧授权。

### 4.4 统一事件系统

目标：让设备、数据、任务和家庭活动通过稳定事件契约协作。

需要补齐：

- 统一事件 Envelope、事件 ID、来源、时间、主体和 Schema 版本。
- 订阅、过滤、持久化、去重、顺序和重放能力。
- 事件级权限过滤和敏感字段脱敏。
- 边缘节点离线后的补发与冲突处理。
- 标准事件目录，如 `device.offline`、`asset.imported`、`task.overdue`。

验收标准：

- 业务模块不通过私有回调形成不可追踪的跨域耦合。
- 消费者重启后可安全恢复处理，不重复产生副作用。
- 未授权订阅者无法从事件中推断敏感家庭信息。

### 4.5 确定性自动化引擎

目标：支持“事件 + 条件 + 动作 + 状态”的可靠家庭自动化。

需要补齐：

- 时间、事件、状态和地理围栏触发器。
- 条件、分支、等待、延迟和人工确认节点。
- 去重、防循环、超时、重试和补偿。
- 模拟运行、版本管理、启停和完整执行历史。
- 自然语言可以生成或修改规则，但落盘格式必须可验证、可审计。

验收标准：

- 自动化在不调用 LLM 的情况下也能按已保存规则执行。
- 相同事件重复投递不会重复产生危险副作用。
- 用户能在启用前看到触发条件、权限需求和预期动作。

## 5. P1：形成应用与设备生态

### 5.1 统一应用模型

明确平台概念边界：

| 类型 | 职责 |
| --- | --- |
| Skill | 模型遵循的工作方法和知识 |
| Tool | 单个可调用能力 |
| Connector | 外部账号或服务连接 |
| Plugin / App | 可安装的软件包，可组合工具、页面和后台任务 |
| Agent | 具有身份、记忆和权限的执行主体 |
| Automation | 确定性的触发与执行流程 |

App Manifest 至少声明名称、版本、发行者、权限、工具、页面、后台任务、数据范围、兼容平台、迁移脚本和签名信息。

验收标准：应用可以被安全地发现、安装、启用、停用、升级、回滚和卸载，卸载时明确处理其数据。

### 5.2 隔离应用运行时

需要补齐：

- 独立进程或容器隔离。
- 文件、网络、密钥和设备能力的最小授权。
- CPU、内存、运行时间和并发限制。
- 工具调用审批、熔断和紧急终止。
- 密钥按调用注入，不写入 Agent 工作区或日志。

验收标准：第三方应用默认不能读取主机文件、家庭私有数据或任意访问网络。

### 5.3 完整设备生命周期

需要补齐：

- 安全配对、设备身份、证书轮换和撤销。
- 在线、离线、休眠、故障和最后同步状态。
- 能力发现、远程配置、OTA 更新和恢复出厂。
- 设备转让、移除和数据清理。
- 弱网、断网下的本地执行与恢复同步。

验收标准：设备丢失、被盗、转让或长期离线时都有明确且可验证的安全处置流程。

### 5.4 局域网发现与云—边—端调度

需要补齐：

- 局域网设备发现和可信配对。
- Home Assistant、Matter 等标准适配层。
- NAS、PC、手机等节点的能力与负载登记。
- 根据隐私、延迟、成本和可用性选择执行节点。
- 本地与云端推理的显式路由策略。

验收标准：关键家庭自动化在互联网不可用时仍可运行，恢复联网后能安全同步状态。

## 6. P2：提高可信度与日常可用性

### 6.1 家庭状态图

维护统一的家庭当前状态，并为每项状态记录来源、更新时间和置信度。Agent 必须区分已确认、推测、过期和未知状态。

### 6.2 活动与解释中心

统一展示发起者、决策 Agent、授权依据、数据访问、执行步骤、结果和撤销入口，避免信息散落在聊天、任务、设备和日志页面。

### 6.3 可恢复事务

跨设备和跨服务操作需要持久化状态机、旧状态记录、用户取消、超时恢复、失败补偿，以及服务重启后的续跑能力。

### 6.4 注意力与通知管理

支持优先级、勿扰时间、消息合并、多通道降级、已读状态、紧急升级和成员级隐私过滤。

### 6.5 备份与灾难恢复

支持加密增量备份、恢复演练、单资源恢复、家庭迁移、数据导出和删除，以及数据库和版本升级场景的恢复验证。

### 6.6 系统健康与可观测性

提供面向普通用户的设备、服务、任务、存储、数据库、模型成本和自动化健康视图，并能导出经过隐私处理的诊断包。

## 7. 推荐实施顺序

1. 统一资源 ID、资源类型和关系表达。
2. 在现有智能家居命令目录基础上建立统一能力契约。
3. 将细粒度权限和审计接入资源、能力与后台任务。
4. 统一家庭事件契约，并实现持久化、去重和重放。
5. 建立确定性自动化引擎。
6. 深化设备状态、离线执行和可恢复事务。
7. 定义 App Manifest 和隔离运行时。
8. 建设应用分发、边缘节点调度和家庭状态图。

任何阶段都应先完成纵向闭环，再扩展资源类型或厂商适配。例如，先让一种灯具从发现、授权、状态同步、自动化到审计完整可用，再扩大设备覆盖面。

## 8. 阶段性里程碑

### M1：统一控制平面

- 核心资源拥有统一身份和关系模型。
- 设备和服务通过标准能力被调用。
- 所有敏感调用经过统一授权和审计。

### M2：可靠家庭自动化

- 标准事件可以持久化、重放和去重。
- 自动化不依赖 LLM 在线执行。
- 跨设备操作可以取消、恢复和补偿。

### M3：安全应用平台

- 第三方 App 具备 Manifest、权限声明和隔离运行环境。
- 安装、升级、回滚和卸载形成完整生命周期。
- 用户能理解并控制应用访问的数据和能力。

### M4：家庭 AI 操作层

- 家庭关键能力支持离线运行。
- 系统能够在本地、边缘和云端之间选择执行位置。
- Agent 基于带来源和置信度的家庭状态进行建议或操作。
- 用户可以通过对话管理资源、权限、设备、应用和自动化，同时保留确定性控制入口。

## 9. 后期项目规划：Rust 加固

Rust 仅用于收敛高风险系统边界，不以重写 FastAPI、业务服务或数据库仓储层为目标。优先处理不可信输入、本地文件系统、外部进程和大文件流式处理；默认采用“独立二进制或受限 Worker + 长度前缀协议”的集成方式，获得故障、权限和资源隔离。只有无法独立部署且接口足够小、可稳定打包时才考虑 PyO3。

### 9.1 第一阶段：设备文件运行时

将 Device Runtime 的路径解析、扫描、哈希、复制和移动逐步收敛到独立 Rust 运行时：

- 基于目录句柄和相对路径执行文件操作，避免“检查后再打开”的 TOCTOU 竞态。
- Linux 使用 `openat2` 等内核约束；Windows 校验句柄最终路径并拒绝越界 reparse point / junction。
- 按 capability 授权，限制扫描数量、单文件大小、并发、CPU 和 I/O。
- 复制与移动采用原子操作，默认拒绝覆盖，并以低权限身份运行。

验收标准：路径穿越、符号链接或 junction 逃逸、命令重放和资源耗尽测试全部通过；Rust 运行时崩溃不能带倒 HomeMind 服务。

### 9.2 第二阶段：安全归档与导入

建立统一的 Rust 安全归档工具，覆盖工作区导入导出、系统备份恢复、家庭数据导出和 Skill / Plugin 安装：

- 限制压缩前后字节数、文件数、目录深度和压缩比。
- 拒绝绝对路径、`..`、重复文件名、特殊 Windows 路径、符号链接、硬链接和设备文件。
- 流式校验与解压到隔离临时目录，全部成功后原子提交。
- 对 ZIP/TAR 解析器持续执行模糊测试和跨平台路径语义测试。

验收标准：归档处理的内存使用不随解压后总大小线性增长；zip bomb、路径逃逸和部分失败不会污染目标目录。

### 9.3 第三阶段：媒体与文档解析隔离

将图片、EXIF、文档和 OCR 解析放入无网络、低权限、可替换的受限 Worker。Rust 负责格式嗅探、任务协议、输入输出预算和进程生命周期；不因使用 Rust 包装而默认信任底层 C/C++ 编解码库。

- 限制像素数、页数、输入和输出大小、CPU、内存与墙钟时间。
- 每个任务使用独立临时目录，解析器崩溃只影响当前任务。
- 根据实际内容而不是文件扩展名选择解析器。

验收标准：恶意或损坏媒体不能使主服务退出、长期占用资源或读取任务目录以外的数据。

### 9.4 第四阶段：Bridge、出站网络与命令代理

- Bridge：在 Rust 层验证帧长度、字段数量、递归深度、Base64 预算、HTTP method/path/header allowlist、nonce 和重放窗口。
- 出站网络：仅在建设统一 outbound proxy 时迁移，统一执行 DNS/IP 绑定、每次重定向复验、特殊地址拒绝、响应大小和超时限制。
- 命令代理：优先覆盖可被网络触发或需要高权限的外部命令，为每个操作固定 executable、参数 Schema、工作目录和环境变量，并管理完整进程树、超时、输出上限、脱敏与审计。

验收标准：任何远程输入都不能构造任意 HTTP 请求、任意子进程参数或无界响应；超时和取消后不遗留子进程。

### 9.5 暂不 Rust 化

- FastAPI 路由、Pydantic 模型、家庭与 Agent 业务编排。
- SQLite/PostgreSQL Repo、i18n、配置和第三方 API 适配层。
- 已由成熟原生库实现的单次 SHA-256、HMAC 或 Fernet 调用。

Rust 能降低内存安全风险，但不会自动修复权限设计、业务越权、TOCTOU 或资源耗尽；每项迁移仍需 capability、配额、OS 沙箱、审计和故障恢复共同完成。

## 10. 桌面运行端后期开发规划

桌面运行端以 `desktop/` 下的 Wails 壳和绿色 Python 运行时为基础，目标是从“能够启动 HomeMind”演进为可长期驻留、可恢复、可诊断、可安全升级的本地运行端。后期工作优先保障实例归属、运行时可信度和故障恢复，不把增加设置项或平台特性置于稳定性之前。

### 10.1 P0：运行安全与稳定闭环

#### 单实例与后端归属

- 使用操作系统单实例机制；第二个进程只负责唤醒已有窗口或传递深链接。
- 后端启动时生成随机 instance token；健康响应返回产品标识、协议版本和 token。
- 只有 HTTP 200 且产品标识、协议版本和 token 匹配时才认为后端就绪，不能把任意 `2xx`—`4xx` 响应视为健康。
- 启动前检测端口占用；支持自动选择可用端口，或向用户显示可操作的冲突提示。
- 明确桌面壳、后端进程和 `OCTOP_HOME` 的所有权，避免多个实例同时升级运行时或操作同一数据库。

验收标准：重复启动只保留一个管理实例；非 HomeMind 服务占用端口时不会被加载；桌面端只停止自己启动并验证过的后端。

#### 可信升级与安全解压

- 为桌面安装包和绿色运行时提供签名及 SHA-256 manifest，并校验平台、架构和版本。
- 拒绝归档中的路径逃逸、符号链接、硬链接和特殊文件，限制文件数、单文件大小、解压总大小和压缩比。
- 解压到随机临时目录，完成结构与可执行文件验证后原子替换。
- 保留上一版本；新运行时未通过启动和迁移验证时自动回滚。
- 保留 SQLite 升级前一致性备份；PostgreSQL 明确由外部系统负责备份恢复。

验收标准：损坏、错误平台、签名无效或恶意归档不能覆盖现有运行时或目标目录外文件；升级任一步骤失败后仍能启动上一版本。

#### 进程生命周期与故障恢复

- 关闭时依次执行应用级优雅退出、有限等待、进程组终止和最终强制清理，不能无期限等待。
- 记录后端退出码、异常时间、自动重启次数和最终状态。
- 启动失败页面提供重新启动、重新检测端口、打开日志目录、复制诊断、导出诊断包、回滚运行时和恢复备份等操作。
- 区分端口冲突、连接失败、数据库迁移、认证异常、运行时缺失和后端崩溃，不只展示通用超时。

验收标准：桌面端退出后不遗留其管理的子进程；连续恢复失败时用户无需终端即可完成诊断、重试或安全回滚。

### 10.2 P1：桌面管理能力

#### 服务控制中心

- 展示服务的启动中、运行、异常、恢复中和停止状态。
- 支持启动、停止和重启，并展示当前地址、端口、PID、运行时长及版本。
- 提供基础 CPU、内存、磁盘占用、最近异常和重启次数视图。
- 端口配置必须形成完整交互：校验范围和占用状态，并在变更后明确重启服务；若改为自动端口，则删除无效的用户配置入口。

#### 更新、备份与恢复

- 分别展示桌面壳版本和 HomeMind 运行时版本。
- 支持手动检查更新、稳定版/测试版通道、更新说明、下载进度、取消和延迟安装。
- 更新完成前验证签名，失败时自动回滚并保留可理解的原因。
- 提供备份列表、来源和目标版本、时间、大小、恢复验证及保留清理策略。
- 恢复旧备份前先创建当前状态快照，避免恢复操作本身不可撤销。

#### 日志与诊断

- 桌面壳日志与后端日志分离，按日期或大小轮转并限制总占用。
- 支持查看最近日志、打开日志目录和导出脱敏诊断包。
- 崩溃报告默认只保存在本地，必须经用户确认后才能发送。
- 诊断信息包括客户端与运行时版本、平台架构、端口、退出码、最近升级结果和数据库类型，但不得包含 token、密码或完整家庭内容。

### 10.3 P2：系统集成与体验完善

- 注册 `homemind://` 深链接，覆盖聊天、任务、日历和审批等稳定路由；第二个实例把链接交给主实例处理。
- 系统通知携带可持久化路由，应用重启后点击旧通知仍能到达正确页面。
- 保存并恢复窗口尺寸、位置、最大化状态和显示器；显示器变化时回退到可见区域。
- 提供“启动时显示主窗口或仅驻留托盘”选项，以及可选的全局快捷入口。
- 防休眠增加“仅在后台任务运行时启用”，避免长期无条件阻止笔记本休眠。
- 根据真实需求评估文件关联和“使用 HomeMind 打开”，不得默认扩大本地文件访问权限。

### 10.4 代码与性能优化

- 移除通过 `reflect` / `unsafe` 修改 Wails 私有事件字段的实现，优先使用公开 API；确需兼容层时集中封装并执行启动自检。
- 健康请求统一使用带连接、响应头和总超时的 HTTP client，并使用有上限的指数退避。
- Dashboard 与桌面壳建立版本化的 ready handshake，在导航完成后注入一次桌面能力，替代固定次数和固定延迟的 JavaScript 重试。
- 设置文件使用“同目录临时文件 + `fsync` + 原子 rename”，并校验端口、时间格式和枚举；损坏文件保留副本供诊断。
- 测量冷启动、首次解压、首屏、空闲 CPU/内存、健康轮询、托盘长期驻留、后端恢复和日志增长；没有基准数据时不做推测性重写。
- 服务稳定后延长健康轮询周期，异常恢复期间再缩短；避免后台空闲状态持续高频唤醒。

验收标准：桌面端 Go 测试、各平台原生打包、安装/卸载、升级/回滚、重复启动、端口冲突、休眠唤醒、多显示器和长时间驻留测试均通过；Windows、macOS、Linux 的行为差异有明确记录。

### 10.5 推荐实施顺序

1. 单实例、严格健康握手和端口归属。
2. 运行时签名、安全解压和失败回滚。
3. 有操作入口的错误恢复页面和可靠的进程树关闭。
4. 服务控制、日志轮转和诊断导出。
5. 更新中心与备份恢复。
6. 深链接、通知持久路由和窗口状态恢复。
7. 清理 Wails 私有 API 依赖。
8. 根据端到端基准优化启动、轮询、内存和能耗。

## 11. 性能提示

- **先测量后迁移**：为候选路径记录吞吐、P95/P99 延迟、峰值内存、CPU 时间、磁盘 I/O 和失败率；没有基准数据时不以“Rust 更快”为理由改写。
- **优先消除无界行为**：先设置文件数、压缩比、像素数、响应体、队列、并发和子进程输出上限，再做语言迁移。
- **保持流式处理**：上传合并、哈希、归档、媒体和 Bridge body 不得整包载入内存；大文件采用固定缓冲区和背压。
- **减少跨语言调用**：若采用 PyO3，应提供批量、粗粒度接口，避免逐文件、逐块或逐帧跨越 Python/Rust 边界。
- **避免阻塞 asyncio**：CPU 密集或同步文件工作进入受限 Worker；Python 事件循环只承担编排和异步 I/O。
- **并发配额必须原子化**：上传空间、任务并发和缓存预算应在数据库事务或单一调度器中预留，不能依赖“先查询、后写入”。
- **隔离比微优化优先**：对图片、文档、OCR 和外部命令，独立进程带来的资源控制与故障隔离通常比 FFI 内的少量性能提升更重要。
- **控制制品复杂度**：Rust 二进制必须覆盖 Linux、Windows、macOS 和目标 NAS 架构，并纳入 wheel/容器构建、签名、SBOM、漏洞扫描与回滚流程。
- **保留可回退路径**：按 capability 或配置灰度启用新运行时，协议版本明确；失败时可安全退回现有实现，不允许静默产生不同结果。

性能验收以端到端工作负载为准。Rust 方案至少应在安全边界明显收敛，或在目标硬件上产生可复现的吞吐、延迟、内存收益之一；否则保留现有 Python 实现。

## 12. 非目标

- 不开发操作系统内核、硬件驱动或通用窗口管理器。
- 不以功能数量代替统一平台契约。
- 不允许 LLM 绕过权限、确认或确定性执行引擎直接实施高风险操作。
- 不为追求“全自动”牺牲用户知情权、撤销能力和家庭隐私。
